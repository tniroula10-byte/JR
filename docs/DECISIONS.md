# Architectural & Implementation Decisions (`docs/DECISIONS.md`)

This document records all defaults and architectural choices made during autonomous implementation of **John Rambo**, consistent with the specification and prioritizing security, privacy, correctness, reliability, maintainability, and UX polish.

| ID | Area | Decision | Rationale |
| :--- | :--- | :--- | :--- |
| **D-01** | **Auth & Session Strategy** | Passwordless Magic Links only (`shouldCreateUser: false`). In Mock Mode (when Supabase keys are absent), an interactive Role & Persona Switcher cookie (`jr_mock_session`) simulates authenticated sessions for `boss`, any of the 4 `employee` accounts, any `customer` account, or `suspended` / `unauthenticated` states. | Allows complete E2E testing of middleware, layout guards, role-based permissions, and multi-context interactions before live Supabase credentials are provided, while keeping production auth strictly locked to invited magic links. |
| **D-02** | **Boss Singleton & Bootstrap** | Enforced via partial unique index `CREATE UNIQUE INDEX profiles_single_boss_idx ON public.profiles ((role)) WHERE role = 'boss';` plus a `BEFORE INSERT OR UPDATE` trigger blocking client role mutations. Bootstrap is exclusively via `scripts/seed-boss.ts`. | Guarantees at the PostgreSQL engine level that a second boss can never exist and no privilege escalation can occur from client requests. |
| **D-03** | **Invitation Authority & Audit Trail** | Single server-side invitation dispatcher (`inviteUserAction`) checks caller role: `boss` can invite `customer` or `employee`; `employee` can invite `customer` only; `customer` cannot invite anyone. Every invite creates an `invitations` row (`status = 'pending'`), pre-provisions `profiles` (`status = 'invited'`, `invited_by = caller.id`), writes `audit_log` and `activity_events`, and sends the magic link. | Satisfies Decision 3 and Section 13 invite rules with full auditability and zero client-side bypass. |
| **D-04** | **Structural Staff Anonymity** | `public.messages` and `public.ticket_messages` store `sender_kind = 'staff'` and `customer_sender_id = NULL` for staff replies. The actual `staff_id` is stored in `public.message_attribution` and `public.ticket_message_attribution`, which have RLS policies granting `SELECT` **only** to `public.is_staff()`. | Customers can never discover which employee wrote a message, even by inspecting raw network payloads, Supabase Realtime frames, or crafting custom PostgREST queries. |
| **D-05** | **Customer Employee Selection Alias Isolation** | When `app_settings.customer_can_pick_employee = true`, customers fetch selectable staff exclusively through `public.get_selectable_staff_aliases()`, a `SECURITY DEFINER` RPC returning `(staff_id, public_alias)` where `customer_selectable = true` and `accepts_tickets = true`. | Prevents customers from querying `profiles` or `staff_profiles` directly while still letting them request a preferred handler by public alias. |
| **D-06** | **Offer Sanity Cap & Validation** | Offers are stored in integer paise (`bigint`), must be `>= 100` paise (₹1) and `<= 100,000,000` paise (₹10,00,000) and `<= listed_price_paise * 2`. Only one active (`pending` or `countered`) offer per `(customer_id, product_id)` is allowed at a time. | Prevents integer overflow, negative/zero offers, and spam flooding on a single product. |
| **D-07** | **Rate Limiting Implementation** | Dual-layer rate limiting: in-memory token bucket (`lib/rate-limit.ts`) for Server Actions/API routes (login emails: 5/15m per email+IP; offers: 10/hr; tickets: 5/hr; messages: 30/min) plus database-level window checks inside `submit_offer`, `create_ticket`, and `send_customer_message`. | Works seamlessly in both Mock Mode and Supabase Production without requiring an external Redis cluster for 60 accounts. |
| **D-08** | **Mock vs. Supabase Adapter Switching** | `lib/data/index.ts` inspects `process.env.NEXT_PUBLIC_SUPABASE_URL` and `process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY`. If they are missing or match placeholder values (`your-supabase-anon-key-here`), it selects the stateful `MockDataRepository` (persisted across Next.js server invocations via `globalThis` + optional local JSON snapshot for multi-context E2E tests). | Enables full Playwright multi-browser real-time chat, offer negotiation, and ticket workflows even without external credentials. |
| **D-09** | **Money & Time Formatting** | All currency values are stored as integer paise (`number` in TS, `bigint` in PG) and formatted via `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'INR' })`. All timestamps are UTC ISO-8601 strings formatted in `Asia/Kolkata` (`IST`). | Eliminates floating-point rounding errors and satisfies Decision 11. |
| **D-10** | **Service Worker & PWA Security** | Service Worker (`app/sw.ts` / `public/sw.js`) caches only static assets (`/icons/*`, `/_next/static/*`, `/offline`) and explicitly bypasses `/api/*`, `/auth/*`, Supabase REST/Realtime endpoints, and RSC payloads (`NetworkOnly`). | Guarantees that sensitive customer chats, offers, or staff data are never cached on shared devices after logout or suspension. |
| **D-11** | **Product Direction Override (2026-11-03, confirmed by operator)** | Supersedes AGENTS.md Decisions 1 and 11 and D-09: login is email/username + password via Supabase Auth (bcrypt-hashed, never stored by the app); money is US dollars (integer cents) and times are shown in US Pacific time. Kept: customer approval queue, "JR Family" all-staff threads. Removed: daily spin bonus. | Client requirements; matches the UI delivered in commit `676e5a1`. |
| **D-12** | **Demo Auth Gating** | `lib/supabase/env.ts`: demo persona cookies (`jr_mock_user_id`, `?as=`) are honoured only when no live Supabase keys exist AND (`NODE_ENV !== 'production'` OR `JR_ALLOW_DEMO_AUTH=1`). With live keys only a validated Supabase session (`auth.getUser()`) counts; without keys in production every protected route fails closed. The demo cookie is `httpOnly`. | Removes the account-takeover backdoor while keeping local demo mode and the Playwright suite working. |
| **D-13** | **No Silent Mock Fallback for Identity** | `SupabaseDataRepository.getProfileById/getProfileByEmail/authenticateWithPassword/verifyEmailOtpAndSetPassword/changeCustomerPassword` use Supabase only; a missing row means no access. The `jr-live-db/state.json` storage dump was removed. | Mock fallback in live mode let demo identities and data leak into production. |
| **D-14** | **Customer Reads via Sanitized RPCs** | Tables whose rows carry staff ids (`conversations`, `offers`, `offer_events`, `tickets`, `ticket_events`, `complaint_*`, `customer_announcements`, `stories`, `app_settings`) are SELECT-able by staff only. Customers read `c_*` / `list_*` SECURITY DEFINER functions returning camelCase JSON with staff ids removed or replaced by aliases. `messages` and `ticket_messages` (no staff ids) stay directly readable so Realtime works. | Enforces Decision 4 structurally in the database, not in the UI. |
| **D-15** | **No Direct Client Writes** | All INSERT/UPDATE policies on business tables were dropped; every write is a SECURITY DEFINER RPC that re-checks role, scope and input, writes audit/activity/notifications atomically, and enforces rate limits in SQL. `srv_*` functions (invite provisioning, username/password admin, auto-close) are executable by `service_role` only; `EXECUTE` is revoked from `anon`. | Closes the "customer edits own offer/ticket" holes and makes rate limits hold across serverless instances. |
| **D-16** | **Invite Flow** | Staff invite → Auth user created with `email_confirm: true` → `srv_provision_invite`. With an initial password the account is `pending_approval`; without one it is `invited` and Supabase emails a 6-digit code (Magic Link template with `{{ .Token }}`) that the customer enters on /login to set a password, moving to `pending_approval`. Staff approve customers; only the Boss approves employees. | Matches the approved UI while keeping passwords inside Supabase Auth (bcrypt). |
| **D-17** | **Local Supabase Counts as Live** | `hasLiveSupabaseKeys()` accepts `http://127.0.0.1` / `localhost` URLs so the real adapter can be tested end to end against `npx supabase start`. | Lets every change be verified against Postgres + RLS before touching the hosted project. |
| **D-18** | **Staff Selection by Alias** | Customer-facing staff lists (`get_selectable_staff_aliases`, `list_reportable_staff_aliases`) return the unique `public_alias` as the selection key; `create_ticket(p_requested_employee_alias)` resolves it server-side. | Customers never receive a staff UUID (Decision 4), even for the complaint dropdown. |
| **D-19** | **Per-User Pages Are Always Dynamic** | `getCurrentProfile()` reads cookies before any branch and the customer/boss/employee layouts export `dynamic = 'force-dynamic'`. | Prevents Next.js from prerendering and caching a signed-in page at build time. |
| **D-20** | **Login Lockout Counts Failures Only** | A successful password login clears its rate-limit key. | Stops legitimate users on several devices from being locked out. |
| **D-21** | **Price Negotiation Happens in Chat** | Operator decision (2026-11-03): customers have no "make an offer" form; they negotiate with John Rambo Support in chat. The offer tables, RPCs and staff queue remain (tested) but customers cannot start an offer from the UI. The misleading "New Product Offer" link was removed. | Matches the client's current UI (catalog shows "Message Support"). |
| **D-22** | **Game Top-ups (operator request, 2026-11-03)** | Customer: Games → pick one of ≤11 active games → amount + game username (remembered per game) → one of ≤3 active payment methods, each showing one payment tag → request. Staff get an unread chat message + notification and mark it Loaded / Payment not received (one time); the customer is notified in chat. Tag rule is a Boss setting: `rotate` (everyone sees the current tag; it advances after N deposits, default 5, counted at request time) or `sticky` (each customer keeps one tag per method; new customers go to the least-used tag; staff can reassign). The tag is resolved in the database at submit time. No payment screenshot; no online payment processing (payments happen outside the app). Rate limit 10 requests/hour/customer. Migration `00004_game_topups.sql`. | Client workflow. Operator was advised that rotating personal P2P payment tags can trigger payment-provider account freezes and that real-money game top-ups may be regulated; compliance is the client's responsibility. |
| **D-23** | **Dependency Policy** | Patch security issues with the smallest compatible upgrade (stay on Next 15, Tailwind 3, TypeScript 5); take majors only when the fix exists nowhere else (zod 4, vitest 5, Resend 6). Unused packages are removed rather than upgraded. Next's bundled PostCSS is forced to the patched root version via `overrides`. | Security without churn before launch. |
| **D-24** | **Durable Auth Throttle** | Failed password logins, invite-code attempts and password-change re-verifications are counted in Postgres (`auth_attempts`, SHA-256 keys, service-role only): 5 per account / 15 min and 30 per IP / 15 min. Fails closed if the throttle cannot be checked. Demo mode keeps the in-memory limiter. | In-memory limits do not hold across serverless instances. |
| **D-25** | **Error Alerts by Email, Not Sentry** | `instrumentation.ts` `onRequestError` emails `ALERT_EMAIL` (message, route, digest only; no request data), each distinct error at most once per 15 minutes per instance. Node-only code sits inside the `NEXT_RUNTIME === 'nodejs'` check so it is stripped from the Edge bundle (an unguarded import made every request 500 in production). | One fewer account for a 25-user launch; uses the same email provider. |
| **D-26** | **Uploads Limited to Story Media** | The UI has no product images or avatars, so only story image/video uploads were built: one-time signed upload URL (permission + type + size checked on the server, bucket limits enforced by Storage), file stored under the uploader's id, `create_story` only accepts an existing file in the caller's folder, viewers get 1-hour signed URLs, expired media removed nightly. Calls Resend's REST API directly instead of the SDK. | Build what the screens use; fewer dependencies. |
